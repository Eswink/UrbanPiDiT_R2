# 用目标长文驱动一轮自主迭代

## 何时使用

- 要把一次迭代或战役写成 **goal 目标**（`/goal <objective>`、无头 `--target <objective>`）：
  长文落 `docs/goals/`，objective 只放要点 + 指向该文件的路径（R-034）；
- **harness 的 goal 模式不可用**：客户端没有该命令、objective 超 4000 字符被拒、
  独立 verifier 读不到你要它核对的证据、完成校验调用在这条 provider 上历史上不成功
  （两种失败形态见下节）、或需要跨多个人工会话看护；
- **用户明确不要 harness goal**，但想要同样的纪律（交付物清单、预算、停止条件、不自行宣布完成）；
- 目标已存在，要按它的 §2 交付物与 §8 进度块继续推进或收尾。

**不适用**：

- 单步修改（直接做，写目标的开销大于收益）；
- 纯方案设计或 TODO 撰写 —— 那是 `planner-delegation`（本技能可以**调用**它产出草稿，但不替代它）；
- issue 推进与 DONE 判定（`issue-lifecycle`）、结果定稿（`result-freeze`）、实验执行（`bounded-study-run`）。

## 前置条件

1. **授权边界必须显式存在**，且引用既有授权 —— 授权**不随任务继承**：
   `docs/goals/full-auto-campaign.md:33-46`（可自主项与仍禁止项）、
   `docs/goals/open-issue-resolution.md:179-198`（自迭代边界）；
   `docs/goals/iteration-campaign.md:19` 明写"授权按 goal 显式授予"。
2. **逐轮时长与记账必须写出数字**：按决策 0029，campaign 无总 GPU-h 上限；逐轮自设
   `planned_seconds`（软）与 `hard_cap_seconds`（宽松硬上限，默认约 2× 计划，按整轮墙钟），
   在长文写死并于实验前纳入冻结协议。超软预算不中止，记录 `soft_overrun_seconds`；硬截断记
   `budget_limited`/`failed` 并全额记账。账本的 cap/used/remaining 是会计字段，不再是授权闸门。
   旧 4/24 GPU-h、单次 ≤30 min 等数字仅作为历史引用保留在各自文件里，不据此重建现行上限；
   数据与付费资源等保留授权边界不变。
3. **判据是已冻结的文档指针**，不得在本目标里新写阈值；`docs/rules/` 与已冻结的证据文档才是判据的写定地。
4. **起点事实**：`git rev-parse HEAD`、相关产物路径、未决项、判据所在文件。
5. 先想清 **谁判定完成**：harness 可用时是独立 verifier；不可用时见步骤 6。
6. **开工前看一眼校验路线**（只影响「自动校验能否收尾」，不影响本轮工作本身）：校验跟随会话的
   **模型选择**，是一条**非流式**调用、在客户端**没有超时**。用只读查询复核当前 provider 的最近一条
   校验是否成功（`~/.zcode/cli/db/db.sqlite`，`query_source='target_completion_verification'`）；
   已知 `new-provider-4`（cline-pass 路由）在该表里 6/6 未成功，分布见
   `docs/R7_ZCODE_GOAL_VERIFIER_ABORTS.md` §2.4。收尾纪律见下节的两种形态处置。
7. **若本目标属于一个 campaign（当前是主模型 V2）**：开工前先读主计划
   `docs/goals/main-model-v2-campaign.md` 的当前节点与 §3 对表清单，跑
   ```bash
   .venv/bin/python tools/check_campaign_state.py
   ```
   退出码必须为 0。它查的是**机械可判定**的四件事（规则号 `C-01`…`C-06`，属该工具自己的命名空间）：
   节点一致性、账本算术与证据指针、上一轮证据已登记、本轮长文结构与 `<!-- round-node: X -->` 标记。
   任一条对不上（或它列出了「无机器支撑的账本行」而你无法解释）⇒ **停下问用户**，不得自行选方向——
   工具通过只表示「与主计划不矛盾」，不表示方向正确（决策 0025）。

## 步骤

1. **侦察**。记录起点 SHA、预算余量、未决项与判据文件；确认要引用的产物还在、且本轮不会覆盖它。
2. **写长文** `docs/goals/<kebab-slug>.md`（不编号 —— 目标是可被取代的活文档），骨架固定：
   `§0 objective（可粘贴）` → `§1 现状（带 file:line）` → `§2 交付物清单 D1..Dn（每条带证据形态）` →
   `§3 判据与证据来源（文档指针）` → `§4 实施顺序（依赖，不跳步）` → `§5 预算与停止条件` →
   `§6 与 planner 草案的差异（若委派过）` → `§7 明确不做` → `§8 进度块`。
   属于 campaign 的目标还要：文件里写 `<!-- round-node: X -->`（X = 主计划的当前节点号），
   §1 写明本轮的由来（引用上一轮 §8 的下一动作与主计划节点），收尾时**回写主计划 §8**
   （`current_node` / `previous_node` / 账本三行与 `<!-- campaign-state: {...} -->` 状态块）。
3. **产出 objective**：**单段、无换行**、≤4000 字符（按 code point 计），**自带交付物清单** ——
   因为 verifier 不能调工具、读不到文件，判据必须能在对话里当场核对；
   结尾写明"不要自行宣布目标完成"。把同一段粘进 `§0` 与文末，并标注实测字符数。
4. **过校检器**（本技能配套的只读工具，非阻断）：
   ```bash
   .venv/bin/python tools/check_goal_brief.py --brief docs/goals/<slug>.md
   ```
   退出码 0 是落地前提。它只查结构（objective 块、字符上限、是否指向自身、交付物/判据/预算节），
   **不判断内容真伪**；写法见最后的规范示例。规则号（校检器自有命名空间，**不是** `docs/rules/`
   的 `R-0xx`）：`G-01` 位置与文件名 · `G-02` objective 节与引用块 · `G-03` objective 单段 ·
   `G-04` objective ≤4000 code point · `G-05` objective 指向本文件 · `G-06` 交付物节 ·
   `G-07` 判据节且含 `docs/**.md` 指针 · `G-08` 预算/停止节；建议项 `A-01` 缺进度块 ·
   `A-02` objective 未标注实测长度。
5. **选定驱动**：
   - **harness**：把 objective 交给 `/goal`；每轮结束更新 `§8 进度块`。
   - **手工循环**（goal 不可用或用户不要）：每轮固定动作 = 读 `§2/§3/§5` → 只做"下一项第一个具体动作" →
     实跑验证 → 更新 `§8`（状态、证据、未做）→ 按 `AGENTS.md` 的九项如实报告 → **本轮结束即停**。
     不做后台续跑、不重开定时器（`docs/R7_MANUAL_ITERATION.md:29-30`、`docs/R7_TASK_QUEUE.md:188`）。
6. **独立复核替代**（harness verifier 不可用时）：机械门禁（`check_conventions.py`、相关测试）+
   证据绑定精确 SHA/run id + `planner-delegation` 的交叉复核。**这三者都不是 verifier**，
   都不能给"完成"定论；状态只能由用户或下一轮以新证据重审后推进。
7. **收尾**：治理层 `git add`（R-037）、在分支内提交、核对 CI（17 条实验 workflow 的 skipped
   是 commit-message 标签门控，不算失败，见 `ci-workflow-triage`）；报告九项并写明
   "下一项的第一个具体动作"。属于 campaign 的轮次还要回写主计划 §8 并让
   `check_campaign_state.py` 在收尾时仍退出 0（CI 里它是 `Check campaign state` 步骤）。
8. **跨会话继续**：从 `§8` 的"下一动作"起步；先复核起点 SHA 与预算余量，再动代码或产物。

## 检查点

- **步骤 1 后**：授权表与预算余量**能写出来**吗？写不出就停 —— 不得靠猜，也不得沿用别的目标的额度。
- **步骤 3 后**：objective 是**单段**且 ≤4000 吗？交付物清单**在 objective 里**可核对吗（不能只指向文件）？
- **步骤 4 后**：校检器 0 失败。手改文档让它通过而不修内容，等于绕过门禁。
- **步骤 5 后（手工循环每轮）**：本轮只推进一项吗？未做与失败如实写了吗？`§8` 与证据一致吗？
- **收尾前**：谁判定完成？执行者没有这个权力（`docs/goals/README.md:22`）。
- **campaign 轮每轮收尾后**：`check_campaign_state.py` 仍退出 0 吗？主计划 §8 的节点、账本与
  状态块跟着这一轮更新了吗（决策 0025）？

## 常见失败

- **把目标写成计划或决策**：计划进 `docs/plans/`（编号 + R-032 的实际结果）、
  决策进 `docs/decisions/`（R-033）、目标进 `docs/goals/`（不编号）——三条线各归其位。
- **objective 塞进全部细节**：超 4000 或变成多段，粘贴即失败；细节属于长文。
- **判据落在文件里而 verifier 读不到**：等于判据不存在；objective 里必须有能当场核对的条目。
- **把历史上限或已被取代的旧额度当成现行闸门**：决策 0029 后无总 GPU-h 上限，逐轮软/硬
  时长仍须先写清并冻结；记账字段不是许可，常设下放也不包含付费资源或新数据授权。
- **在手工循环里假装有 verifier**：自己宣布 `complete`。状态机是
  `active / paused / budget_limited / complete`，执行者只能提议，不能宣布。
- **依赖自动续跑**：本仓明确"无后台续跑、不重开定时器"；一轮结束就是结束。
- **把 skip / 取消 / 排队的运行当通过**（`AGENTS.md:19`）。
- **为了报告好看而放宽判据或改测试**；负面结果照写才算完成。
- **回溯改写老目标文件**：它们是证据；新约定只约束之后写或重写的目标。
- **把校验器的两种失败形态当成目标失败**：见下节——会话被打断、或校验调用悬挂，都是客户端已知问题，
  恢复后从 `§8` 续跑即可。

## 完成校验的两种失败形态与恢复（客户端已知问题，2026-09-28 / 2026-09-30 定位）

goal 的「完成校验」是**回合结束之后**的一次独立模型调用（`querySource: target_completion_verification`、
非流式、`tools: []`、携带整段对话）。它在这台客户端上有两种已定位的失败形态——**都不是判据失败，
也不影响本轮工作本身**：

| 形态 | 你看到的现象 | 判据（本地可核） | 处理 |
| --- | --- | --- | --- |
| ① 被 provider 判为非 JSON | 会话在「目标未完成、要求继续」时**被打断**并恢复（会话重启、上下文被摘要） | rollout 日志末行 `AI_APICallError: Invalid JSON response` | 从 `§8` 续跑；不要依赖自动结项 |
| ② 长时间不返回（路径**无超时**） | UI 停在「第 N 次迭代 · 目标校验中」，该会话新输入被**排队** | `session_entry` 最新校验条停在 `status:"started"`；`model_usage` 行 `status='cancelled'` + `cancelled_by_user=1`、时长 20+ 分钟 | 在会话里**暂停/停止**（`/goal pause`）→ 按下表核验三处终态 → 按 `§8` 手工续跑 |

完整证据（时间线、代码偏移、26 次校验调用按 provider 的分布）见
`docs/R7_ZCODE_GOAL_VERIFIER_ABORTS.md`；决策 0024 把「自动校验按 best-effort、不依赖它结项」
写成本仓约定。形态②的三处终态判据：`session_target.status` 不再是 `active/verifying`
且 `active_run_started_at` 为空；最新校验 `session_entry.payload.status` ∈ {`cancelled`,`failed_closed`}；
`model_usage` 无 `status='running'` 行。

**因此本技能多三条纪律**：

1. 一个 goal 会话只跑一轮；**每次推进都更新 `§8` 进度块**（恢复后的新会话据此续跑，不必重读全部历史）；
   单条命令的输出保持简短（长输出写文件再引用摘要）。
2. **回合内先把结论写完再结束回合**——校验发生在回合结束之后，且它可能失败或悬挂。
3. 看到「目标校验中」停住超过约 10 分钟、或看到「目标未完成」后会话立即消失，就按上表处理：
   不要反复发消息（会被排队），也不要当成判据失败。

**不要依赖自动结项**：校验失败或取消时目标状态不会被判定。

## 完成判据

- `§2` 的交付物逐条有证据（精确 SHA、run id、digest 或测试名与结果），未做的写明"未做"；
- 校检器 0 失败，且 `§8` 与证据一致；
- 治理层已被 git 跟踪（R-037 的意图，不只看它是否报错）；
- 是否 `complete` 由用户或独立复核裁定，报告中**不**自行宣布；
- 若发生降级（harness→手工循环、planner 不可用），在报告与 `§8` 里如实写明。

## 明确不覆盖

- **不做科学判定**：阈值、判据、DONE 定义写在 `docs/rules/` 与已冻结证据文档里，不写在目标里；
- 不替代 `planner-delegation`（方案设计）、`issue-lifecycle`（推进/关闭）、
  `result-freeze`（结果定稿）、`bounded-study-run`（实验执行）；
- **不产生证据**：长文与 objective 都不是运行记录，也不是产物；
- 不覆盖 harness 的实现细节；objective 上限或 verifier 行为变化时，按 R-034 的复核触发重审本技能。

## 规范示例（校检器接受的最小目标文件骨架）

下例保留旧的**结构示例**，只展示 G-01..G-08 接受的骨架，不是决策 0029 后的实验预算模板。
新目标必须按前置条件 2 写明 `planned_seconds`/`hard_cap_seconds`：超软预算继续并记录 overrun，
只在硬上限因时长截断。不要复制下例的「授权余量之内」「超预算即停」或把 GPU-h 数字当总额度闸门。

```markdown
# 目标：example-goal-brief

本文件是 goal 模式的目标长文源。objective 见 §0；交付物见 §2；预算与停止条件见 §5。

## 0. objective（可直接粘贴，单段 216 字符，实测 ≤4000）

> 本轮目标：把一件可核对的事做完（起点 SHA 开工时用 git rev-parse HEAD 记录）；交付物清单与判据见 docs/goals/example-goal-brief.md。交付物：D1 写出实现与测试并实跑；D2 把实测数字写进证据文档。纪律：不新增阈值、不放宽已冻结判据。预算与停止：本轮 ≤0.5 GPU-h，超出即停并如实记录。结束时报告启动 SHA、改动面、实跑验证、未做的事与下一项。不要自行宣布目标完成。

## 1. 现状

- 起点：`git rev-parse HEAD`（开工时记录）。

## 2. 交付物清单

| # | 交付物 | 证据形态 |
| --- | --- | --- |
| D1 | 实现与测试 | 测试名与实跑结果 |
| D2 | 证据文档 | 文件路径 + 实测数字 |

## 3. 判据与证据来源

- 判据只有既有比较器的逐 seed 同号规则，见 docs/R7_B2_MULTISEED.md；本目标不新增阈值。

## 4. 实施顺序

1. 写实现与测试；2. 实跑；3. 写证据文档。

## 5. 预算与停止

| 项 | 值 | 依据 |
| --- | --- | --- |
| 本轮上限 | ≤0.5 GPU-h | 既有授权余量之内 |
| 停止条件 | 超预算、测试失败、门禁违规 | 如实记录后停止 |

## 7. 明确不做

- 不新增数据下载、不改默认值、不合并 main。

## 8. 进度

- 状态：active
- 已完成：无
- 未做：全部
- 下一动作：写 D1 的测试
```
