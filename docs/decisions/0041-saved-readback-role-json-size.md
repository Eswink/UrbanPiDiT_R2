# 0041 保存读回角色 JSON 的单文件工程上限统一为 64 MiB

- **日期**：2026-10-08
- **状态**：accepted

## Context

S3 保存读回曾为每个角色文件额外设置 2 MiB 工程上限，低于读者已有的 64 MiB JSON 上限。
完整角色记录可能超过该较小限制；仅为满足 2 MiB 而引入压缩容器、解压协议和额外资格核验，
会让结果登记承担不必要的格式工程成本。该尺寸限制不是天气性能或统计接受判据。

用户在本次侧聊明确要求放宽这项限制：“非要 JSON 这么短，给个 64 MB 嘛”。
本决策按已有 JSON 上限采用 64 MiB，即 67,108,864 字节。

## Decision

1. 新的保存读回协议将**每个角色 JSON 文件**的最大字节数由 2 MiB 调整为 64 MiB，
   与单 JSON 解析上限一致。限制按实际编码后的字节数判断，而不是字符数。
2. 保留普通 JSON 保存和读回；不为满足旧 2 MiB 限制强制压缩、拆分或删减字段。
   全部字段、类型、有限性、原始字节摘要及 source/checkpoint/data 身份核验保持不变。
3. 该变更仅前瞻应用于新协议和新产物。已经冻结的源码、协议、失败回执与产物不原地修改，
   不将旧尺寸失败追认为通过；并发执行者收到授权后在新的读回实现中采用此上限。
4. 累计读量、路径范围与软硬时限仍按新协议实际准入核对。角色文件的单项限额不是授权
   读取七份 64 MiB 文件多次；读量预算按实际文件尺寸和读取次数重新计算，不因本决策自动扩大。
5. 不改变模型、真实数据、开发停止出口、科学判据、test 曝光/确认序号，亦不授权新增训练或评分。

## Consequences

**变容易的：** 完整角色记录可直接保存为 JSON，免去只为较小尺寸门而引入的压缩与解压链，
减少格式兼容故障和登记等待；统一的 64 MiB 上限也更容易理解和维护。

**变难 / 代价：** 单个文件的最大读取、解析内存和磁盘开销增加。调用方仍需先检查实际尺寸，
将所有实际读取计入既有累计预算；不能把单文件 64 MiB 当作无总量约束。

**兼容性：** 新写者允许超过 2 MiB 的完整 JSON，旧冻结读者仍可能拒绝，故须绑定新协议和
对应读者身份，不以修改旧回执或放宽科学比较器解决兼容问题。没有新依赖。

**备选方案与否决理由：** 不采用仅为维持旧 2 MiB 门而强制无损压缩的方案；压缩不是错误，
但在本项用户已授权合理单文件上限的情况下，其新增协议、解压边界及复核成本不必要。
