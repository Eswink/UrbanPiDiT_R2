# 0120 — 取代 0119 的探针口径：安静机器上的边际速率 + 串行探针

- **日期**：2026-11-26
- **状态**：accepted
- **取代**：决策 **0119** 的 `probe()` 口径（`REFUSAL_FRACTION` 与「400 updates 的总速率」这一对）
- **不取代**：0119 的增益公式、区域口径、四个出口的全部判据、归因边界
- **`scientific_claim: false`**、`test_read: false`、`r = 0`

## Context

attempt01 的探针判 `refused-insufficient-envelope` 并拒绝开训（treated 2.6077 / 2.6731 s/upd，
占剩余包络 0.7277 / 0.7425 > 0.60）。按冻结规则停轮是正确行为，但**读数本身是错的**，
而这个错误的来源在 0119 的执行记录里被误判过一次，本 ADR 先把它改正。

### 0119 执行记录里那条诊断是错的（实测推翻）

0119 的执行记录写「400 步窗口把约 300 s 启动成本摊成 ~0.9 s/upd，边际速率其实是 1.58」。
它依据的是一次 **60 updates** 的复测。本 ADR 用同一个 `fine_tune_long_rollout`、同一份权重、
同一 `batch_size=2` 重测，**直接看 400 步内四个区间的边际速率**：

| 区间（on 臂 `visit_damped`，独占整机） | 边际 s/upd |
| --- | ---: |
| updates 0–100 | **1.075** |
| updates 100–200 | **1.098** |
| updates 200–300 | **1.110** |
| updates 300–400 | **1.109** |

**从第 0–100 区间起速率就是平的**，没有任何「启动摊销」的下降趋势。累计速率
（1.10 s/upd）与边际速率（1.10 s/upd）**相等**。所以：

- 「400 步窗口太短、启动成本摊不薄」**是错的**。400 步足够，且启动成本小到看不见。
- 「边际速率 1.58」**也是错的**；那是 60 步样本的噪声，被当成真值写进了 ADR。

### 真正的原因：探针运行时机器被占用

两个实测对照，都在 `batch_size=2`、同一权重、同一条训练路径上：

| 场景 | 边际 s/upd |
| --- | ---: |
| **独占整机，单 worker** | **1.103** |
| **两卡各一个 worker，同时跑** | **1.0796 / 1.0921** |
| **attempt01 的探针（两卡各一个 worker）** | **2.48 / 2.58 / 2.65 / 2.48** |

前两行说明**并发本身不是原因**：两张卡各跑一个 worker，速率与独占时相同。
第三行是探针的实测，比前两行慢 **2.3 倍**。

差别在**同一时刻还有别的 CPU 负载**：探针在 01:05 落盘，而我从 00:37 起在同一台机器上跑
**全量测试套件（6,040 passed / 1,301 s）**。训练加载器是
`DataLoader(..., num_workers=4)`（`training/r7_long_rollout_runner.py:381`），
**数据供给是 CPU 密集的**；测试套件把 CPU 占满时，loader 供不上，GPU 空转等 batch。

⇒ **探针测的是「机器当时有多忙」，不是「这轮训练有多快」。** 这是一个**测量环境**缺陷，
不是估计量缺陷，也不是实现缺陷。

### 这个缺陷属于哪一类

0116 那条「探针早停」的设计是对的：包络是一个预测，探针让它可被证伪，测不动就在 400 步
拒绝而不是烧十小时。本 ADR **保留**这个形态。要修的是**探针的测量条件**与**速率估计量**：

1. **测量条件**：探针期间不得有其他 CPU/GPU 负载（尤其是全量测试套件）；
2. **估计量**：用**后段边际速率**而不是全程总速率——不是因为启动成本大（实测它很小），
   而是因为总速率会把任何早期抖动永久摊在结果里，而边际速率只反映**当前**的供数速度。

## Decision

1. **`probe()` 的速率估计量改为后段边际速率**：取本轮探针中最后 1/4 更新区间的
   `Δelapsed / Δupdate`，与总速率**一并记录**。两者相差超过 25% 时，以边际速率为准并在
   `probe.json` 里写明差值与原因。
2. **探针期间禁止并发 CPU 负载。** 执行者必须在探针开始前确认机器安静，并把当时的
   `loadavg` 与 `nvidia-smi` 利用率写进 `seed{N}_probe.json`。**这不是一个新判据**，
   是测量条件的记录；违反它不算科学失败，算无效测量，必须重跑探针。
3. **包络按实测边际速率重定。** 实测 on 臂 **1.10 s/upd**（两个场景一致），
   取 **1.30 s/upd** 作为冻结常数（高于两个实测值 18%，覆盖 `uniform_damped` 臂与波动）。
   单 seed 需要 `2 × (2,400 × 1.30 + 3,200) = 12,640 s`。`PER_SEED_SECONDS` 取
   **25,280 s**（2.0×），硬包络覆盖两波。
4. **`REFUSAL_FRACTION` 保持 0.60。** 理由：过滤掉「跑不完」的轮次这个目的没变；
   变的是速率输入的质量，而阈值本身没有证据说要改。**本轮不因为在安静机器上测出 1.10
   就调低它**——那样会让同一份数据既当诊断又当门限。
5. **四个出口、增益公式、区域口径、归因边界一律不变**（0119 Decision 5 与 Context ①②③
   原样有效）。本 ADR 只动探针。
6. **新 attempt，不重跑旧 attempt。** attempt01 已冻结、其探针读数已作为
   `record:s3-visit-gain-probe-refused` 登记，**不得**在它上面覆盖或续跑。

## Consequences

**变容易的：**

- 探针从「机器忙不忙的读数」变回「这轮多快的读数」；1.10 vs 2.5 的 2.3 倍差距被定位到一个
  可核查的外部原因（同期 6,040 个测试），而不是留成一个「实现好像很慢」的悬案。
- 包络从 2.0× 的 1.55 s/upd 预测换成 2.0× 的 1.30 s/upd 实测上界，单 seed 12,640 s 的需求
  在 25,280 s 里有 2.0 倍余量；总预算 3 seed 两波 ≈ 8.4 GPU-h，低于 0119 的 11.1 估算。

**变难 / 代价（如实列出）：**

1. **0119 的执行记录里那条「启动摊销」诊断是错的，且已登记进证据页。**
   本 ADR 更正它，但**不改**已登记的 `record:s3-visit-gain-probe-refused` 正文；
   那条记录里 `marginal_seconds_per_update_off=1.583` 应读作「60 步样本，噪声大于信号」。
   正确的值见本 ADR 与新一轮的 `probe.json`。
2. **「安静机器」不是一个机械判据。** 它是执行纪律，靠执行者声明 + 记录 `loadavg`。
   我没有把它做成自动门限：自动门限需要选一个 `loadavg` 阈值，而所选阈值会直接决定轮次
   能不能跑，那是一个会改变通过率的判据，应由证据而不是顺手决定。
3. **1.30 s/upd 只由 on 臂、单 seed、160–400 步的样本支撑。** `uniform_damped` 臂未单独测；
   两者代码路径差别只是常数，但这是**推测**，所以常数取了 18% 余量而不是贴着 1.10 定。
4. **本轮仍未回答 A−B。** 本 ADR 只是让那次测量可以开始；读数在 `readings.json` 之前不存在。

## 备选方案与否决理由

- **备选 A：把探针拉长到 2,000 步。** 否决：实测 400 步的速率已经平（四个区间 1.075→1.109），
  拉长不增加信息，只增加拒绝前的沉没成本。问题的根源是同期负载，不是窗口长度。
- **备选 B：只改 `REFUSAL_FRACTION` 到 0.80 就能过。** 否决：那是把一个错读数迁就过去。
  0.7277 与 0.7425 之所以超 0.60，是因为速率被污染的 2.3 倍，不是因为包络太紧。
- **备选 C：保留 0119 的 1.55 s/upd 常数，只改估计量。** 否决：1.55 是在**未测**时按
  in-protocol 轮的 1.43–1.45 加余量猜的；现在有了 1.10 的实测，继续用一个猜的常数会让包络
  比实际需要大 41%，白占硬上限。
- **备选 D：让探针也记录 `loadavg` 但不改变任何行为。** 部分采纳：记录是 Decision 2 的一部分，
  但**同时**必须禁止并发负载，否则记录只是事后解释，不能防止同样的污染再发生一次。

## 执行记录（attempt02，2026-11-26）

**未决 2 已由实测回答**：`uniform_damped` 并不比 `visit_damped` 慢。四个臂的训练速率
（2,400 updates 各自实测）：

| seed | `visit_damped` | `uniform_damped` |
| ---: | ---: | ---: |
| 41 | 1.1301 s/upd | **1.1294 s/upd** |
| 42 | 1.1523 s/upd | 1.1572 s/upd |

两条臂相差 ≤ 0.5%，且都在冻结常数 **1.30** 之下（余量 ≥ 12%）。所以「两者代码路径只差一个常数、
速率应当相同」这个**推测**，现在有实测支持；1.30 对两臂都成立，包络无需再定。

**探针制度本身也通过了检验**：attempt02 的探针（安静机器）判放行，占比 0.4925 / 0.4988，
而同一实现在 attempt01（同期跑测试）判拒绝、占比 0.7277 / 0.7425。同一个门限在两个测量条件下
给出不同结论，且差异方向与「污染使速率虚高 2.3 倍」的实测一致——这说明本 ADR 改的是**测量条件**，
不是**门限**。

**未决 1（A−B 读数）**：已产出，见 `docs/R7_S3_VISIT_GAIN_RESULT.md`。**出口 ① 为假**
（72 h 上 A−B 在 seed41 为 **+0.000323 K**、seed42 为 **−0.001023 K**，符号翻转）。
