## Context

本轮的预声明出口（`docs/goals/s3-capacity-or-architecture.md` §3，冻结于开跑前）写的是：

> 72h 三 seed 全正 → 提请独立验收；否则关闭"**靠加大容量解决 72h**"这一支，转架构或数据方向，
> 不再加 seed、不重复同一 test、**不无限调容量**。

随后，工作态笔记 `.zcode/plans/s3-architecture-lit-2026-10-13.md` §3 提出一条新候选假设 **H-D**：
只把主干 `dim` 从 192 提到 256/320，其余逐字不变，并主张**先于** plan 0022 的 H-A/H-B 测它。
依据是 arXiv **2602.22962**（Yu / Huang / Calotoiu / Hoefler, *Scaling Laws of Global Weather
Models*, 2026-02-26, cs.LG）摘要原文：weather forecasting models **consistently favor increased
width over depth**，并建议 prioritize **wider architectures**。

**冲突是直接的**：H-D 就是"加大容量"。按冻结原文，它落在被关闭的那一支里；而"不无限调容量"
正是这条出口要防的事。**在灰色地带推进它，等于事后放宽一条已冻结的判据**——本仓明令禁止。

两侧的证据都不是空的，但都不是"必须开 H-D"：

- **支持把容量继续往下走一点**：本仓自己的意图写在 `docs/RESOURCE_BUDGET.md:19`——
  "后续**只有在消融证明容量不足时**再增加宽度/深度"。本轮 depth 4→8 的读数正是这样一次消融；
  而"**深度**轴无收益"推不出"**宽度**轴无收益"。
- **反对把 2602.22962 当作强依据**：同一段摘要的 compute-optimal 结论是"固定算力下
  **数据 > 模型规模**"，即它排序里**数据排在模型前面**——而数据轴按本轮 Objective 的 D3 明确
  **暂缓、放到最最后**。该论文拟合的是 GraphCast 36.7M 到 Aurora 1.3B 的**全球基础模型 + 40 年
  ERA5**，与本仓"区域 + 少数据 + 3.29M 参数"不可直接类比；且笔记只读到摘要。
- **"宽度轴尚未试过"这句话必须收窄**：当前主线上 `dim` 确实一直是 192（注册协议里 186 处
  `192/depth 4`），但注册协议里**存在**宽度变体——`dim` 为 32 / 128 / 248 / 384 的臂分别出现在
  `r7_b0_learnability`、`r7_74_autoregressive`、`r7_b1_d1(_run2)`、`ms_probe`、`r7_multiseed_real`
  等；索引里 `b1-d1-controlled-comparison` 是 `unresolved`、`b2-multiseed-negative` 是 `negative`。
  准确表述只能是"宽度在**当前主线**上尚未单因素试过"，不是"历史臂一直是 192"。

**时序（如实记录，不得省略）**：本 ADR 作出时，本轮 **seed 41 的读数已经可见**——
`interior_32` t2m 72h RMSE 3.5604 K vs 对照臂 3.5965 K（Δ −0.0360 K），72h skill **−0.1512**
（对照臂自身 −0.1746），即 72h **仍为负**。**本 ADR 不改任何阈值、任何门、任何判据，也不预设
本轮三 seed 的结论**；它只回答"出口关闭的是哪一根轴"，并为"最多还能开几个容量臂"设一个上界。

## Decision

1. **出口收窄**：§3 出口所指的"靠加大容量解决 72h"读作**深度轴**——即本轮作为唯一单因子所测的
   `depth` 4→8，而不是整条容量轴。
2. **宽度是独立轴**：在当前主线上尚未单因素检验；它不因深度轴关闭而自动关闭。
3. **封顶（binding，本决定最重要的一条）**：**宽度是最后一个容量臂**。若宽度臂也未能让 72h 三 seed
   全正，则**整条容量轴（深度＋宽度）永久关闭**——此后**不得**再开任何容量臂：不得重试 `depth`、
   不得再扫 `dim`、不得做宽＋深组合、不得以"再调一点容量"为名复活该支。之后只剩训练信号 / 目标
   组织 / 数据方向（数据按本轮 D3 暂缓，放到最最后）。
4. **宽度臂的准入条件**：必须单因素、可证伪、带正负控制；且 brief 里**必须显式处理**
   "宽度没有逐位恒等扩张"这件事——实测 `dim` 192→256 时 state_dict 的 155 个张量里 **150 个形状
   变化**（共同键 155、形状不同 150），已登记的 v3-BD 1600 父状态（dim-192/depth-4）**装不进去**。
   depth 那轮靠 identity-gated 镜像 + 输出投影清零做到了"起点逐位等于注册函数"（`encoder_bit_identical`）；
   **宽度没有这种构造**，因此"宽度"这一因素必然与"初始化/优化轨迹"混杂。该混杂必须写进 brief 并
   在读数里如实标注，不得照搬 depth 的"单因素保真"措辞。
5. **成本口径更正**：H-D 不是"更省成本"。实测参数量 `dim` 192/4 = 3,286,037；
   192/8 = 5,065,493（+54%，即本轮）；**256/4 = 5,790,389（+76%，比深度那轮还大）**；
   320/4 = 8,999,253（+174%）。宽度臂优先于 H-A 的正当理由是**归因顺序**（先把容量轴结清再动
   架构/训练信号），不是成本。
6. **不改变本轮任何冻结内容**：`protocol.json` / `code.zip` / 证据 / 判据一律不动；本轮读数照原样登记。

## Consequences

**正面**：

- 出口的**适用范围**有了明确文本，H-D 不必在灰色地带推进，也不必靠"再解释一遍"来开工。
- "不无限调容量"从一句原则变成**可核查的承诺**：最多再开一个容量臂，且它的失败条件被预先写死。
- 宽度臂的两个已知陷阱（无逐位恒等扩张、成本被低估）在开工前就被记下，避免 brief 里再出现
  照搬 depth 措辞的错误。

**负面（代价，必须记住）**：

- **时序风险是本决定最大的弱点**。它是在 seed 41 负读数**已经可见**之后作出的，因此存在
  "看数据改规则"的观感风险。缓解手段只有两条：① 正文如实写明时序与本决定不改任何阈值/判据/门
  的事实（已写入 §Context 末段）；② 它**收窄**了容量轴的可选空间（封顶为一个臂）而不是放宽——
  整体上计划更紧，不是更松。**若独立复核认为时序不可接受，正确的补救是放弃 H-D、改走
  `docs/plans/0022` 的架构方向（H-A/H-B/H-C），而不是继续推进 H-D。**
- 若宽度也失败，容量轴关闭后可选空间显著变窄：只剩训练信号 / 目标组织 / 数据，而数据按 D3 暂缓。
- **封顶是自我约束，没有机械闸门**：`tools/check_conventions.py` 无法判定"这是不是又开了一个
  容量臂"，也没有任何校验器读 `correction_record_id`。执行靠留痕与独立复核，不靠工具。
- 本 ADR 不解决宽度臂**该不该做**的问题——它只界定"可不可以做、最多做几个"；宽度臂仍需自己的
  round brief、预声明出口与独立复核。

### 被否决的替代方案

- **不改出口、直接开 H-D**：与冻结原文"不无限调容量"直接冲突，属事后放宽已冻结判据，契约禁止。
- **不改出口、H-D 搁置、直接走架构（plan 0022 的 H-A）**：零规则风险、改动最小，但放弃文献
  依据最强的一根轴。**保留为替代路径**：若审计不接受本 ADR 的时序，改走它。
- **把整条出口作废、重新预声明**：作废一条已冻结出口比收窄它更重，且会让本轮的负读数失去
  预声明意义——那才是真正的"移动门柱"。
- **只写"宽度是独立轴"而不封顶**：等于给容量轴开无限口子，正是这条出口要防的事，不采纳。
