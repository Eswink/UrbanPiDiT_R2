# 0068 — 空间收缩剪除中间 checkpoint：92 处历史审计引用变成悬空，如实登记

- **日期**：2026-10-29
- **状态**：accepted
- **范围**：`outputs/` 下已登记历史轮次的**中间** `update_*.pt`。**不改**任何已登记数字、
  不改任何判据、不改任何协议、**不碰**在跑的 seed43。原始数据（`data/raw|interim|processed`）与归档快照未受影响。
- **依据**：决策 0009（「缩范围解决」= `tools/prune_r7_run_checkpoints.py`，只删非
  `selected_checkpoint` 的中间权重）；`AGENTS.md`「结论**必须**可追溯到运行记录与产物 digest」；
  用户 2026-10-29 明确授权「先做 A，先剪已登记的历史轮」。

## Context

**① 磁盘压力是真实且紧迫的。** `/data` 3.6T 中已用 3.3T，**仅剩 164G（96%）**。
`outputs/` 占 740G，其中 **668.5 GiB 是 16,917 个中间 `update_*.pt`**（每个约 41 MiB）。
seed43 仍在训练（control 已到 4840/16071），跑完两臂预计再需约 54–66 GiB
⇒ 不释放会有中断风险。

**② 执行范围与结果（终态实测）。** 目标 = 50 个有可剪计划的已登记轮次，**排除当前轮**。
用户授权后执行，**全部 50 轮完成**（不是中途停止，更正见 ③）：

- 50 轮全部写 `checkpoint_prune_receipt.json`（含每个被删文件的路径、字节、sha256）
- 共剪除 **10,855 个**中间 checkpoint
- 释放 **477.68 GiB**；`/data` 剩余 **164G → 634G**（**96% → 82%**）
- **12 个 selected endpoint 全部实测存在**（两轮逐一验证）

**③ 发现的时间点：剪枝已完整跑完，不是中途才停。**
执行前我做了一次依赖扫描，只查 `parent_checkpoint`/`selected_checkpoint`/`checkpoint` 等
少数键名，得到「0 处依赖」并据此放行。**那个扫描口径太窄**：它没有覆盖「历史审计记录里
引用中间 checkpoint」这一情形。那份更宽的、按**绝对路径存在性**判定的扫描（扫 4,178 个
JSON、4,278 条 distinct 绝对 `.pt` 引用）是与剪枝**并行**发出的，等它返回时剪枝已经跑完
**50/50**。发现后我立刻终止了残留进程并做了全套只读复核（见 ④），但**删除已不可逆**。

**⚠ 更正（2026-10-29，实测）**：本条初稿写的「剪到第 33 轮主动停止、剪除 5,224 个、
164G→390G」是**中途读数**，不是终态，已作废。终态实测：
**50/50 轮完成**（该 50 轮的 receipt 全部存在）、**剪除 10,855 个**中间 checkpoint
（receipt 汇总）、**释放 477.68 GiB**；`/data` 剩余 **164G → 634G**（**96% → 82%**）。
「主动停止」这个说法是错的：实际是**跑完之后才拿到告警**。

**92 处引用指向已不存在的文件**，全部集中在两轮：

| 轮次 | 悬空引用数 | 被剪 | 引用方 |
| --- | --- | --- | --- |
| `r7_74_autoregressive_20261003_attempt01` | 74 | 2.45 GiB | `r7_74_stats_complement_20261003_attempt0{1,2}/artifact_manifest.json` |
| `r7_73_process_supervision` | 18 | 0.59 GiB | `r7_m3_validation_complement_acceptance_20261002/{readonly_seal,audit_receipt,independent_final_verification,checkpoint_precheck}.json` |

**这两轮确实在我的 50 轮目标清单内**（`grep "^outputs/<run>\t"` 命中），所以
**这 92 处是我今天造成的，不是历史遗留**。涉及空间仅 **3.04 GiB** —— 也就是说，
这 3.04 GiB 的收益换来 92 处证据弱化，是笔坏交易，但因为范围小，影响可控。

**④ 发现后做的复核（实测，全部只读）**：

- 92 处悬空引用按存在性扫描确认；剪枝停止后**重扫仍为 92**（无新增）
- 两轮的 **12 个 `selected_checkpoint` 逐一验证存在**
- 当前轮未被触碰：seed41/42 的 **3,216** 个 checkpoint 完好（各 1,608）

**⑤ 账目口径（实测，必须按此读）**：`outputs/` 下现有 **55** 份
`checkpoint_prune_receipt.json`，但**只有 50 份属于本次**（= 本次目标清单，逐一命中）。
另外 **5 份是 2026-09-27 的历史记录**（`r7_65_c1/c2/c3`、`r7_64_curriculum`、
`r7_recut_multiseed`，共 210 个 checkpoint / 6.60 GiB），**与本次操作无关**，
不得计入本次释放量。

**本次删除的时间线（按 receipt 的 mtime，实测）**：**00:11–01:49 一个连续执行**完成
全部 50 轮，无「两个执行者各剪一半」的情形。因此下文任何把 55 拆成「33+22」的
说法都是错的，见 §Addendum 的更正。

## Decision

1. **如实登记，不掩饰。** 本 ADR 与两轮的 `checkpoint_prune_receipt.json` 一起构成
   「哪些文件被删、为什么、删前的 sha256 是什么」的完整记录。**不**删改任何审计 JSON
   去"修复"引用——那才是真正的篡改。
2. **影响的准确性质：这是可追溯性的弱化，不是可复现性的破坏。**
   - **未破坏**：每个臂的 `selected_checkpoint` 全部保留且实测存在；所有评估目录、
     `rmse.csv` / `boundary_rmse.csv` / `climatology_skill.csv`、`training_report.json`、
     协议与结果 JSON 一律未动。**已登记的数字仍可从保留的端点复现。**
   - **已弱化**：上述 6 个审计 JSON 里写着「我核对过 `update_0000300.pt` 等中间点、
     sha256 为 X」，而这些文件已不在磁盘上。**sha256 值本身仍在该 JSON 里**
     （哈希证据链未断），但**无法再拿文件重新验算**。
3. **不追溯恢复**（不可行）：文件是 `unlink` 删的，无回收站、无备份，磁盘块大概率已复用。
   任何"重建"都是伪造，R-008 明令禁止。
4. **剩余 17 轮暂停，不继续。** 在 ③ 的教训被机械化之前，继续剪是不负责任的。
   恢复条件：先用**按绝对路径存在性**的扫描（即本次用的口径）逐轮确认零悬空，再剪。
   该口径必须写进 pruner 的前置检查，而不是靠执行者记得。
5. **给 pruner 加前置闸门（待实施，不在本 ADR 落地）。** `plan_prune` 应额外返回
   「被删文件是否被任何 JSON 以绝对路径引用」，非空即拒绝——把 ③ 的漏检变成工具级
   fail-closed。**本 ADR 只登记缺陷与教训，实施另行提交并附反证。**
6. **这是一次执行者的判断失误，记录责任归执行者。** 我用了过窄的扫描口径却当成
   完备检查，并在剩余空间紧张的压力下把"0 处依赖"当作充分放行条件。

## Consequences

**变容易的：**

- `/data` 从 96% 降到 82%（剩余 164G → 634G，实测），seed43 跑完两臂的空间风险基本解除。
- 50 轮、10,855 个中间权重的删除有逐文件 sha256 receipt，删除本身可审计。
- 暴露了一个真实缺口：**仓库从没有过"中间 checkpoint 是否被外部引用"的检查**。
  这次是第一次把这个问题摆到台面上。

**变难 / 代价（如实列出）：**

- **92 处审计引用悬空**，6 个历史审计 JSON 里有无法再核验的文件名。这是本条最实质的代价。
- **中间 checkpoint 不可恢复** ⇒ 那两轮无法从中间点重启训练（决策 0009 已记的固有代价，
  此处被放大到"审计引用"层面）。
- 50 轮目标已全部执行完毕；不在该清单内的目录（约 268G 的 `outputs/` 余量里仍有未剪项）未处理。
- 本轮 0 GPU-h，但**不是"无影响"的操作**：它改变了 outputs 的可追溯状态。

**备选方案与否决理由：**

- **备选 A：先做全量悬空扫描再剪，一次做完 50 轮。** 本该如此。否决的是**当时的执行顺序**：
  我先用窄口径扫描放行，宽口径扫描是并行发出、事后才回来的。
- **备选 B：把 6 个审计 JSON 里的引用改成"已剪除"。** 否决：那是修改历史审计记录，
  比悬空引用更严重。正确做法是**另加**一份说明文件，不动原件。
- **备选 C：从备份恢复那 3.04 GiB。** 无备份可取；磁盘块已复用。
- **备选 D：在旧工具下把 50 轮一次剪完。** 这正是实际发生的（因为闸门是事后才加的）。
  结果可接受**纯属侥幸**：92 处引用恰好集中在两轮，其余 48 轮无跨轮引用。
  若当时就按存在性口径逐轮预检，这 92 处本可避免——这个判断不变。

## Addendum（2026-10-29）

**⚠ 本节原稿的两处说法已被实测否定，在此更正，原记录保留以便对照。**

**原说法 A：「55 份 receipt 分属两次执行：先前会话 33 轮 / 5,224 个 / 238.4 GiB；
续跑 22 轮 / 5,841 个 / 245.9 GiB」——错。**
实测（按 receipt 逐份核对 `run` 字段与目标清单）：

| 口径 | 轮次 | checkpoint | 释放 |
| --- | --- | --- | --- |
| 本次目标清单（50 轮） | **50** | **10,855** | **477.68 GiB** |
| 不在目标清单的 5 份 | 5 | 210 | 6.60 GiB |
| 合计（`outputs/` 下全部 receipt） | 55 | 11,065 | 484.28 GiB |

那 5 份**不在目标清单**的 receipt 的 mtime 是 **2026-09-27**，属于历史整理
（`r7_65_c1/c2/c3`、`r7_64_curriculum`、`r7_recut_multiseed`），与本次无关。
按 mtime 聚类，本次是 **00:11–01:49 一个连续执行**跑完 50 轮（00:11–00:27 完成 18 轮，
00:37–01:49 完成 32 轮），**不存在「两个执行者各剪一半」**。
⇒ 「33+22」这个拆分是把 5 份旧记录挤进算术后的产物，作废。

**原说法 B：「续跑发生在闸门落地之前，与 §Decision 4/5 顺序相反」——前提不成立。**
既然 50 轮是一个连续执行，就不存在「先 33 轮暂停、后由另一执行者续跑 22 轮」的顺序问题。
真实顺序是：剪枝**连续跑完** → 宽口径扫描返回 92 处 → 我终止残留进程 → 加闸门 → 复核。

**仍然成立的结论（未被上述更正动摇）**：那 22 轮的审计结论——
「续跑新增 0 处悬空引用，92 处全部落在 `r7_74_autoregressive_20261003_attempt01` 与
`r7_73_process_supervision` 两轮」——其**数值**与我的独立复扫一致（92 处，无新增）。
它对「为什么恰好是那两轮」的解释（跨轮审计引用网络，属经验事实而非结构保证）也成立，
且**正是** §5 要求机械化闸门的理由。

**对 §4 剩余暂停状态的处置。** 50 轮目标清单已全部执行完毕，不存在「剩余 17 轮」；
但 §4 的**恢复条件**（先按存在性口径验证零悬空再剪）仍应在**任何未来新一轮剪枝**前满足。
闸门已实现在 `tools/prune_r7_run_checkpoints.py`（`external_references()` + fail-closed
exit 3 + `--allow-referenced` 显式覆盖 + `--scan-root` 可测），故 §5 的待办**已完成**。

**最终账目（实测）。** `/data` 剩余 **164G → 634G**（**96% → 82%**）；
本次 50 轮逐文件记录路径/字节/sha256；**全部 selected endpoint 实测存在（0 缺失）**。
在跑的 seed43 全程未被触碰：seed41/42 的 3,216 个 checkpoint 完好，
seed43 训练进程健康（检查时已在 8,300/16,071）。
