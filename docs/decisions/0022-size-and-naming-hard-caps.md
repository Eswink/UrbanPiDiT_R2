# 0022 规模硬上限与目录命名：先量后立、例外只许缩小

- **日期**：2026-09-29
- **状态**：accepted

## Context

`docs/rules/size-thresholds.md` 一直是 C 类：R-019/R-020/R-021/R-022/R-023 只报告、不阻断，
理由是"阈值当前有大面积违反，做成门禁会让仓库立刻全红"。这套设计有一个没有被检查的后果：
**数字从来没有人核对**。2026-09-29 的全面测量（E-191）发现本页写「R-021 当前命中 0」而实测是
21，R-020 写 6 而实测 36；更根本的是，尺寸族用的 `CODE_SCOPES` **不含 `tools/` 与仓库根级
模块**，于是全仓最大的文件 `tools/check_conventions.py`（当时 1741 行）对这几条规则完全不可见——
"0 违规"里有一半是范围造成的（E-193）。

命名一侧有同类缺口（E-192）：`NAMING_PY_SCOPES` 同样不含仓库根级模块，8 个入口模块不受任何
命名规则约束；目录名只被 R-043 的杂物桶词表顺带扫到，没有任何大小写形态约束；R-043 的文档把
范围写到 `configs/`、`docs/`、workflow 与根目录文件，实现却只扫活跃 `.py` 文件；R-047 的文档把
顶层 `README.md` 列为豁免，实现却漏了它；R-048 的"0 命中"在参数 `ckpt` 引入后也没同步。

用户（2026-09-29）要求给这三件事——文件命名、函数规则、文件行数——加上真正的约束，
并且明确：**行数上限不要定得太短也不要太长，不要为了达标去重写大多数文件**。

## Decision

1. **先量后立，零改名落地。** 三条新规则都取在实测分布的尾部之外，落地当天仓库就是绿的：
   - **R-051**（阻断）：单文件硬上限 **600** 行。实测文件 p95=580、p99=946，>600 的 13 个既有
     文件全部列入 `FILE_LOC_EXCEPTIONS`（精确路径）。
   - **R-052**（阻断）：函数体硬上限 **200** 行。实测 2,127 个函数中 p99=128、最长 245，
     只有 5 个长编排入口越线，列入 `FUNC_BODY_EXCEPTIONS`（`(路径, 函数名)` 对）。
   - **R-053**（阻断）：代码目录 snake_case；`.agents/skills/<name>/` kebab-case **且必须含
     `SKILL.md`**。实测 16 个代码目录 + 11 个 skill 目录全部合规。
   两个目标态数字（R-020 的 100、R-021 的 400）**保持报告型不变**，形成「目标 + 硬上限」两层，
   与 R-019（硬上限 200，阻断）／R-019b（目标 120，报告）的既有做法一致。
2. **例外是冻结清单，只许缩小。** 每个例外必须是精确路径（无通配符、无目录级豁免）；
   `test_size_exception_lists_are_frozen_exact_and_alive` 把清单成员冻结在测试里，
   并断言**每条例外当前仍然超标**——某个文件被拆分到 600 行及以下时测试失败，强制把该条删掉。
   因此"新增例外"必须显式改测试（评审可见），而"清单自然缩小"是自动的。
3. **阈值只许收紧。** 放宽 600 / 200 或往清单里加条目，等于放宽已冻结的判据，必须另立决策记录；
   正确做法是先拆成模块（`size-thresholds.md` 的例外表就是待拆分清单）。
4. **补齐范围，而不是放宽规则。** 尺寸族的范围独立为 `SIZE_SCOPES`（`CODE_SCOPES` + `tools/` +
   根级模块），命名范围纳入根级模块；其它代码规则的范围不动，避免改变未经校准的判据的输出。
5. **`size-thresholds.md` 加机器核对标记。** `<!-- measured: R-019=0 ... -->` 由
   `test_size_report_counts_match_the_checker` 重算比对，命中数随代码变化时必须同步——
   这正是防住"文档写 0、实测 21"那类漂移的机制。
6. **提交闸门补上空白检查。** `guard_conventions_before_commit.py` 用 git 自己的检查
   （对 HEAD 的增行 + 未跟踪文件整文件）复现 CI 的 `git show --check`，把 E-190 的教训
   （提交里多一个行尾空行，CI 变红）机械化为提交前的拒绝。

## Consequences

**变容易的：** 规模与命名有了可执行的边界，且边界与既有文件不冲突（零重写）；
例外清单即待办清单，"谁还超标"一眼可见；文档数字与实现绑定，漂移会被测试当场拦住；
大文件继续长胖在提交阶段就被拦住，而不是等到某次 CI 失败。

**变难 / 代价：** 例外清单里的两个治理文件（`tools/check_conventions.py` 1,834 行、
`tests/test_check_conventions.py` 946 行）本身也在清单内，往后每加一条规则都让它更接近
"必须先拆分"的状态——拆分它们将成为独立切片，且必须保持规则行为逐位不变；
新增一条规则现在要动六处计数（`README.md`、`MIGRATION.md`、`ci-and-verification.md`、
`AGENTS.md`、`docs/skills/README.md` 与 `test_rule_execution_counts_match_docs`）；
600/200 会让某些"本来会自然长到 800 行的脚本"被迫提前模块化，这是刻意的代价。

**备选方案与否决理由：** "只对新增文件设限"（钩子实现，无例外清单）被否决——它不约束既有文件的
继续膨胀，也无法在 CI 侧复核，本地红与 CI 红会重新分叉；"全仓硬上限 400"（即直接启用 C 类目标态）
被否决——24 个文件越线，等于要求重写大多数，与用户"不用重写大多数"的约束冲突；
"把 13 个超标文件一次性拆完"被否决——拆分是独立的技术工作，混在规则落地里既抬高风险，
也让"规则已生效"这件事无法干净验收。
