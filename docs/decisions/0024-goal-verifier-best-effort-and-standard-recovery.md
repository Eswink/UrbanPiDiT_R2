# 0024 goal 自动完成校验按 best-effort：保留 harness 驱动，收尾不依赖自动结项

- **日期**：2026-09-30
- **状态**：accepted

## Context

本仓用 harness 的 goal 模式驱动长轮次（2 小时量级的自主轮）。轮次结束之后，客户端会发起一次
**独立的完成校验调用**（`querySource: target_completion_verification`，非流式、`tools: []`、携带整段对话），
由它决定目标是否完成、以及是否注入下一轮的续跑指令。

这台客户端上这条调用有两种已定位的失败形态（E-201）：①被 provider 判为非 JSON 响应而**打断会话**
（2026-09-28）；②**长时间不返回**且客户端**没有超时**——2026-09-30 的实例悬挂 1773 秒，
UI 停在「第 1 次迭代 · 目标校验中」，会话新输入被排队，最终由用户暂停中止（写终态 `cancelled`、
目标转 `paused`）。全量 26 次校验调用里，`new-provider-4`（cline-pass 路由）**0/6 成功**，
而 `new-provider`、`account:zai-start-plan` 两条路由 **20/20 成功**（含 53 万输入 token 的大请求）
⇒ 失败与请求体积无关、与所选路由相关。

用户（2026-09-30）在权衡「仓库侧记录 + 本地客户端超时补丁 + 操作性规避」与「长轮次改手工循环」
之后，选择**保留 harness 驱动**，并要求把恢复动作标准化。本决策把这两件事写定。

## Decision

1. **harness goal 仍是长轮次的默认驱动**；但它的「自动完成校验」与「自动续跑」按 **best-effort** 看待——
   **不得**把目标完成判定、轮次推进或证据结论建立在校验结果之上。
2. **完成判定权不变**：只有用户或独立复核能声明 `complete`；执行者只能提议（沿用技能的四态状态机）。
3. **标准收尾纪律**（写入 `goal-loop` 技能与缺陷文档）：
   - 一个 goal 会话只跑一轮，**回合内**先把结论写进证据文档与目标长文 `§8`，再让回合结束；
   - 校验可能挂起：UI 停在「目标校验中」超过约 10 分钟即按缺陷文档 §2.6 处理——
     在会话内**暂停/停止**，并按三处判据核验终态（`session_target.status`、最新
     `session_entry.payload.status`、`model_usage` 无 `running` 行）；
   - **不 resume 了事**：同一路由上会再次失败/挂起；要续跑先换路由（见第 4 条）。
4. **操作性规避（开工检查）**：goal 轮次的会话模型不要选 `new-provider-4`（cline-pass 路由）；
   开工前用只读查询复核该 provider 最近一次校验是否 `completed`。
5. **客户端超时补丁**：在 `~/.zcode/server/agents/glm/zcode.cjs` 上做**本地**补丁，把校验调用包成
   与 10 分钟定时器的 `Promise.race`，使「永不返回」变成一个普通错误、走既有 `failed_closed` 路径。
   它是**仓库外的本地改动**，不进版本控制、客户端更新即失效；位置、覆盖范围与重放步骤记在
   `docs/R7_ZCODE_GOAL_VERIFIER_ABORTS.md` §4 与 `docs/plans/0005-zcode-goal-verifier-hang.md`。

## Consequences

**变容易的：** 校验器出问题时不再有"要不要等它"的犹豫——队列排队与悬挂都有固定的识别签名与恢复动作；
轮次收尾不再依赖一个 0/6 成功的调用；「换一条路由再跑 goal」成为一条有证据支持的开工检查。

**变难 / 代价（如实列出）：**

- 每轮收尾多一步人工核验（三处终态判据），并且**必须**在回合内把 `§8` 写完——写不完就等于轮次没有落点；
- 本地补丁是**未受版本控制保护的系统改动**：客户端更新会静默覆盖它，届时症状回到「无限挂起」，
  重放需要人工按文档定位那处唯一源码串；补丁本身也**没有**在真实挂起场景下端到端复现（见计划 0005 的实际结果）；
- 换路由只是操作性规避：本条依据是**单机单账户的 26 次观测**，不是对上游行为的普遍结论；
  上游若修复或再次变化，本决策的规避条款要重审；
- 本决策不修复客户端，因此形态①（会话被打断）仍然会发生，恢复代价依旧。

**备选方案与否决理由：** 「长轮次改手工循环、harness 只做短目标」被用户否决——本仓长轮次的价值正是
无人值守推进，且实测主回合与工具链本身是稳定的；「只记录、不设默认」被否决——恢复动作不写死时，
下一次仍会停在同一个界面上等人判断；「等待上游修复」被否决——上游报告尚未提交，等待期没有止损手段。
