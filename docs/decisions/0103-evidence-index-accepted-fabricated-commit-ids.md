# 0103 — 证据索引曾接受**伪造的 commit id**：形状校验不等于对象存在，现已拒零填充

- **日期**：2026-11-08
- **状态**：accepted
- **范围**：`docs/R7_EVIDENCE_INDEX.jsonl`、`tools/verify_r7_evidence_index.py`、
  `tests/test_verify_r7_evidence_index.py`。**本条 0 GPU-h、零读数、不改任何冻结判据。**
- **依据**：`tools/verify_r7_evidence_index.py` 的 `COMMIT_RE` 实现（实测）；
  `docs/decisions/0094`（C1 前置否决）与 `docs/decisions/0099`（D1.d 缓冲区对账）两条记录；
  R-001/R-012 的「结论必须可追溯到运行记录与产物 digest」精神

## Context

**① 发现路径是偶然的，不是审计发现的。** 在为 Stage C2 预写登记材料时，我读取索引最后一条
（`s3-whitebox-trained-state`）作为字段模板，注意到它的 `evidence_commit` 是
`fbe5876000000000000000000000000000000000`——一个**以 33 个零结尾**的 40 字符串。
这不像一个真实 SHA-1。

**② 实测：它不是对象。**

```
$ git cat-file -t fbe587600000000000000000000000000000000
fatal: git cat-file: could not get object info
$ git cat-file -t 687175d000000000000000000000000000000000
fatal: git cat-file: could not get object info

$ git log -1 --format='%H' fbe5876
fbe587608a2867c77c93ea001054537bee0b24fb      ← 真正的提交
$ git log -1 --format='%H' 687175d
687175d9b014714fc0745053520c5521004b596a
```

⇒ 两条记录（C1 前置否决、D1.d 白盒化）把**7 字符短 SHA 补零到 40 字符**当成完整 SHA 写进了
索引。**它们指向的提交不存在。**

**③ 为什么校验器没拦住。** `validate_record` 只用
`COMMIT_RE.fullmatch(value)` 判「是不是 40 个小写十六进制字符」。补零串**完全满足**这个形状，
于是 `PASS`。这是本仓反复出现的那类错误的又一例：**「通过了形状检查」被当成「指向了真东西」**。

**④ 影响面已经量化，不是猜测。** 全索引 210 处 commit 字段里，**只有这两条记录（4 个字段）
是补零的**，其余 206 处是完整 SHA（实测遍历 + `git cat-file` 逐一核对：
**修复后 0 处指向不存在的对象**）。所以缺陷是**局部的、由我引入的**，不是长期系统性腐败。
但两条恰好是最近两条 S3 记录，也就是最可能被当作登记范例的两条。

## Decision

1. **修复数据**：把两条记录的 `evidence_commit`/`experiment_commit` 换成**真实完整 SHA**
   （`687175d9b014714f…`、`fbe587608a2867c7…`），并**重新渲染** `docs/R7_CANDIDATE_BRIEF.md`
   （它内嵌这些 SHA，不重渲染就会与索引失同步而被 `--check-brief` 拒绝）。
2. **加机械守卫**：`_is_zero_padded_short_sha` —— 若一个 40 字符串是
   **6–11 位十六进制前缀 + 29–34 个零**，判为伪造并在 `validate_record` 报错。
   错误的形状是「短前缀 + 全零尾巴」，**不是**「以 0 结尾」。
3. **不改 `COMMIT_RE`**：40 位形状检查仍然必要（挡住 39 位、大写、非十六进制）；
   新守卫是**附加**的一条，不替代它。

## Consequences

**负面后果（代价，必须如实列出）**

1. **我修的是数据，不是让校验器去查对象存在性。** 真正的强校验是
   `git cat-file -e <sha>`，但它要求校验器**在工作树里跑且有完整 git 对象库**；
   CI 的浅克隆/裸检出可能不具备，且 `verify_r7_evidence_index.py` 目前是**纯文件读取、
   零子进程**的设计。我选择了**不引入 subprocess 依赖**，代价是：**一个拼错的普通 SHA
   （不是补零形态）仍然能通过**。这一面**没有**被本条关掉。
2. **启发式有边界。** 前缀长度限制在 6–11 位：一个真正的 40 位 SHA 恰好是
   「6–11 位非零 + 29–34 个零」的概率极低但**不是零**；若真出现会**误报**。
   我接受这个风险，因为误报是**拒绝**而不是放行——按本仓「宁可停」的取向，拒绝更安全。
3. **第一版守卫是错的，而且是我自己发现并修的。** 最初的实现用
   `value.rstrip("0")` 判长度，把**两条真实提交**（`…a63d0`、`…dff50`，都合法地以 0 结尾）
   判成伪造 ⇒ 索引当场 `ERROR line 89` / `ERROR line 103`。**这是同一个会话里
   「启发式未在真实数据上验」的第二次**（第一次是 dispatch 的 retry 窗口）。
   记下来是因为它说明：新校验规则必须先在**已有的真实语料**上跑一遍，再提交。
4. **两条被改写的记录，其历史版本的错误没有被单独归档。** 我把它们原地改成正确值，
   没有保留「曾经是补零的」这一状态。可追溯性靠本条 ADR 的实测输出，不靠索引自身。
5. **本条零读数、零 GPU-h**，不构成任何关于 C1/D1.d 科学结论的证据；它只修**引用完整性**。

**正面后果**：把一个「校验通过但指向虚空」的登记缺陷变成了**具体、可复算的实测**
（`git cat-file` 双向证据 + 210 处逐一核对）；把「形状 ≠ 存在」这条教训**机械化**了一次
（16 个测试，含反证：把守卫改成 `return False` 后新测试失败、恢复后 16 项全过）；
并且**没有**把「我改好了」写成「索引现在可信」——第 1 条负面后果明确留着拼写错误的缺口。

**否决**：

- **只修数据、不加守卫**。否决：同样的补零动作下次还会发生，而它**不会**被任何现有检查拦住。
- **让校验器调用 `git cat-file`**。否决：把纯文件校验器变成依赖 git 对象库与工作树的工具，
  在 CI 浅克隆下可能整体失效；那是把「偶发伪造」换成「常态不可用」。
- **用「以 0 结尾」当判据**。否决：**实测**会误杀两条真实提交（见负面后果 3）。
- **保留两条错误记录、只加一条勘误**。否决：索引是机器读的，读者不会去读 ADR；
  错误值留在 `evidence_commit` 里就等于继续指着不存在的对象。
- **声称索引现在完全可信**。否决：普通拼写错误仍在缺口内（负面后果 1）。

## 未决

- 是否值得在**登记时**（而不是校验时）加一条 `git cat-file -e` 检查——那里有完整工作树，
  代价低，但它属于 `tools/r7_round.py` 的写路径，不在本条范围内。
- 其余 206 个字段我只核了「对象存在」，**没有**核「这个提交的树里真的有该 evidence_path
  的那一版字节」。后者更强，需要 `git show <sha>:<path>` 比对，是本条未覆盖的一面。
