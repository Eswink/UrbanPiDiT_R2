# 0008 B2 数据范围：把 D1 段扩到 36 天（train 区间逐位不变）

- **日期**：2026-09-27
- **状态**：accepted
- **上游问题**：`#64` B2 执行顺序第 5 条「首先做 +6h 训练和 6/12/24/48/72h 自由
  rollout」；本会话获得「B2 数据范围（D1 或自行判断的成本可行扩展）」的显式授权。

## Context（背景）

#64 B2 明文要求训练 +6h、并对 **6/12/24/48/72h 做自由 rollout**。D1
（`outputs/r7_d1_earthmover/store/cache.zarr`，120 时次）**做不到 72h**：

- `ZarrRolloutDataset` 的一个 rollout 窗口需要 `history_steps=2` 帧历史
  （1 个历史步 + init）**加上** 12 个 lead 步（72h / 6h）= **14 个连续同 split 时次**；
- D1 的 val 区间是 `[2016-01-25, 2016-01-28)` = 3 天 = **12 个时次**，test 同样 12 个。

**实测证据**（不是外推）：

```
val  lead=48h windows=3
val  lead=54h windows=2
val  lead=72h REFUSED: no complete held-out rollout windows at requested horizons
```

即 D1 上 **72h 自由 rollout 的窗口数为 0**。B1 之所以能报 48h，是因为它用
`lead_hours=(lead,)` 单时效请求（每 run 一个时效，例数 10/9/7/3）；但 72h 仍然
连一个窗口都没有。要满足 B2 就必须让 held-out 块比 D1 冻结时更宽。

## Decision（决定）

**新增一个 36 天工程段（`B2`，144 时次），其 train 区间与 D1 逐位相同**，
split 仍走决策 0005 的 `split_time_ranges` 模式：

| split | 区间 | 时次 | D1 对应 |
| --- | --- | --- | --- |
| train | `[2016-01-01T00:00, 2016-01-25T00:00)` | 96 | **完全相同** |
| val | `[2016-01-25T00:00, 2016-02-01T00:00)` | 28 | D1 是 12（3 天） |
| test | `[2016-02-01T00:00, 2016-02-06T00:00)` | 20 | D1 是 12（3 天） |

- 前 120 个时次就是 D1 的冻结请求（`_requested_times` 断言 D1 末时次落在下标 119），
  因此 **train 区间、train-only 归一化统计、climatology 的 (month,hour) 桶与 D1
  逐位一致**——B1 的 train-only 基线与 B2 的共用同一份训练分布。
- val 扩到 28 时次：72h 自由 rollout 有 **15** 个窗口（28 − 13），48h 有 19 个，
  6h 有 22 个。这是本决定唯一的**目的**。
- test 扩到 20 时次（`[02-01, 02-06)`）：这一段**此前没有任何 R7 实验读过**，
  B2 全程 `test_read: false`，保持封存。

## 成本（按 `docs/R7_D1_READ_SPEED.md:14` 实测单价 8.78 s / 25.15 MiB 每时次）

| 项 | 估计 | 冻结预算 | 判定 |
| --- | --- | --- | --- |
| 网络 | ~3.53 GiB | — | — |
| decoded | ~10.9 GiB | ≤64 GiB | ✓ |
| 墙钟 | ~21 min | 单次实验 ≤30 min（决策 0007） | ✓ |
| 新产物（store） | ~33 MB | ≤16 GiB | ✓ |

**为什么重新下载 120 个时次而不从 D1 归档拼接**：多花的 0.66 GiB 网络换来
「一次请求、一份回执、一个源身份」；拼接会造出第二个来源（D1 归档 +
新片段）而 receipt 说不清它是什么。二者都远在冻结上限内。

## Consequences（后果）

- **变容易的**：B2 可以在**同一份 train 分布**上同时满足「多种子确认性比较」与
  「6/12/24/48/72h 自由 rollout」；B1 与 B2 的 t2m/mslp/v850/t500 数值可直接对比，
  因为训练数据、归一化、target 变量都没动。
- **代价 / 风险**：本段仍是**单一年（2016）1 月**，val/test 仍是工程再划分，
  不是 v2 的 2019 验证年或 2021 test 候选；climatology 仍只有 4 个 (month,hour)
  桶。**任何跨季节/跨年结论依然 UNVERIFIED**，B1 声明的局限逐条继续适用。
- 新增源身份：`outputs/r7_b2_segment/source.nc` 有独立 SHA256 与回执，
  与 D1 是两个数据身份，报告不得混称。

## 放弃的选项与代价

- **放弃「只用 D1、把 72h 从 B2 要求里降级」**：代价是**直接违抗 #64 原文**
  （B2 明文列了 72h），换取 0 成本。不做——判据不得为好看而降级。
- **放弃「扩到完整 62 天（全年 1–2 月）」**：36 天已经让 72h rollout 有 15 个
  窗口；再加 26 天只增加网络/墙钟（+~40 min，超单次 30 min 上限），
  而 val/test 的例数增量对确认性比较的**证据增量**很小。单位预算不支持。
- **放弃「用 D1 的 val+test 拼成一个 24 时次 held-out 块」**：那会让 test
  在调参阶段被读，违反「test 封存」。不做。
