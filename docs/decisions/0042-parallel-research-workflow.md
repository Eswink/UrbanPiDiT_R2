# 0042 并行科研与 workflow 编排能力

- **日期**：2026-10-08
- **状态**：accepted

## Context

用户要求「适当改造项目，让它也能使用 workflow，并行科研设计，能并行才并行，并行之前需要思考能否并行」。
长期主模型超气候态 campaign 会持续产生多个互不依赖的可证伪假设，以及大量可与实验重叠的资料/CPU
准备与只读复核工作，但本仓一直没有规定「何时可以并行、如何隔离与登记」。

- 本仓「workflow」长期只指 `.github/workflows/` 的 CI 标签门控 workflow；ZCode 的 dynamic workflow
  （`CreateWorkflow` 产物存 `.zcode/workflows/`）虽在决策 0001 里定过位置，但**从未实际使用**
  （`docs/rules/EVIDENCE.md:247-248` E-163/E-164：目录不存在、`workflow_definition`/`workflow_run` 表 0 行）。
- 现有并行实践是零散的：多个计划/目标已写「可并行」，但无 SOP 规定准入门槛与隔离要求。
- 安全边界：工具事件载荷无子智能体身份（E-186），子会话很可能不跑 hook（E-187，**推测**，
  `AGENTS.md:155-156`），因此并行子代理不能依赖 hook 兜底。
- 准入规则的张力：`docs/skills/README.md:9` 要求能力「已重复 ≥2 次且步骤固定」，而本能力只有
  「并行已被**计划** ≥3 次」的先例（`docs/plans/0004-r7-main-model-v2.md:183`、
  `docs/goals/s2-climatology-mechanism-screening.md:54`、`docs/goals/n4-m5-confirmation.md:75`），
  **尚无 ≥2 次实际并行执行** —— 故本决策按用户明确要求**前瞻准入**，并把首次真实并行轮的留痕验证写成硬要求。
- 历史：2026-10-08 曾有一版 goal+workflow 组合方案被用户叫停并回滚，未给出失败理由；本次由用户
  **明确要求**重启该方向，故范围收窄到治理/技能/文档层。

## Decision

1. 新增能力 `.agents/skills/parallel-research-workflow/SKILL.md`，把并行科研与 workflow 编排固化为
   可复用流程，并在 `docs/skills/README.md` 与 `AGENTS.md` 路由表登记。
2. **准入优先**：任何并行前先过七条 gate（假设独立、产物隔离、计算资源、数据实例、可变状态、
   可独立验证、多重比较纪律）；任一不满足即串行，并把结论与理由写进文档。
3. **编排形态分级**：串行（默认）→ 普通 Agent 扇出 → dynamic workflow 脚本（仅在确有控制流或阶段
   依赖时）。脚本属工具运行态，不进版本控制（R-035）。
4. **安全**：并行子代理默认只读，写只写各自排他 `outputs/`；禁写受保护数据、归档、既有产物与已跟踪
   测试；GPU 仍由统一父调度按共驻余量**串行**（R-054）；不把安全寄托于 hook。
5. **科学完整性不变**：每臂独立 `protocol.json` + digest + 证据页 + index record；test 保持封存；
   `r`/alpha 纪律不放宽；**并行不等于共享预算**，各臂分别记账。
6. 范围限**治理/技能/文档层**：本决策不改生产模型与训练代码，不新增机械检查器；并行轮次的机械
   校验留待真实重复后另立（`docs/skills/README.md:9` 的准入规则）。
7. **前瞻准入（准入例外）**：本能力尚不满足 `:9` 的「重复 ≥2 次且步骤固定」——只有「并行已被计划
   ≥3 次」的先例。依据是用户明确要求项目支持 workflow 与并行科研，故**前瞻立 SOP**，并强制：
   首次真实并行轮必须留痕验证并写进 goal §8 / 计划；若实践显示步骤不固定或并行不可行，
   应修订或撤下技能与 `docs/skills/README.md` 的登记行，不得长期停留在未验证状态。

## Consequences

**变容易的：** 独立研究线可同时推进；资料/CPU 准备不再阻塞实验；「能否并行」有可核对的判断依据，
不再靠直觉；dynamic workflow 脚本有了合法且受约束的入口。

**变难 / 代价（如实列出）：** 并行放大资源争用与多重比较风险；子代理可能绕过 hook，安全只能靠
只读/隔离写约定与 Stop hook/CI 兜底；dynamic workflow 通道在本仓从未验证过，首次使用必须留痕、
不得假定可用；并行臂的证据与账本登记工作量增加，容易漏行——现有 `check_campaign_state.py`
只校验已存在账本行的算术与指针，**发现不了缺行**（本仓已发生过一次：index63 已登记而账本缺行）。

**备选方案与否决理由：** 不采纳「只在主计划写一句并行、不立能力」（无法约束后续轮次）；不采纳
「同时加机械检查器」（违反 `docs/skills/README.md:9` 的「重复 ≥2 次才立 SOP」，且新代码/测试/基线
成本高于当前收益）；不采纳「直接用 dynamic workflow 脚本做所有编排」（无控制流时只增加复杂度）。

本决策不取代 0030/0038/0039 的授权边界，不改变任何科学判据与冻结证据。
