## Context

**① 已登记的 22 条 negative / 23 条 mixed，有一批是在约 1 epoch 的算力下判死的。**
R1 控制臂只把 updates 从 2,400 提到 16,071（数据不变）就让 72 h skill 从 `+0.0258` 走到
`+0.1527`；R2 在算力匹配后把同一机制由「2/3 绝对门」翻成四出口全真
（72 h skill `+0.264772/+0.263564/+0.284917`，配对改善 15/15）。这不等于那些支会翻，
但它等于**它们没有被公平检验过**——「在算力不足的 regime 下判死」与「方法无效」不是同一句话。

**② 主目标的「物理信息」那一半从未被实验过。** 全仓唯一的物理正则化是空间一阶差分惩罚，
且 `gradient_lambda = ZERO_GRADIENT_LAMBDA = 0.0`（`training/r7_recursive_losses.py:18`）、
不在任何已登记协议里；散度/涡度只作**前向输入**（`model/r7_process_tensor_diagnostics.py:133,139,145`）
无惩罚项；8 向量过程诊断损失权重 `0.0`；质量守恒 / 静力平衡 / 连续方程 / 谱损失 / CRPS
**全仓零命中**；legacy 有完整的 `legacy_v531_full/losses/physical_consistency.py:248,280`
但**当前代码不 import**。⇒ 这是空白，不是失败。

**③ 转向的核心前提被本轮 Stage A 的实测部分推翻（如实记录）。**
计划 0028 §0.4 把 2.42–2.63 s/update 归因于「95% 时间在单线程 zarr 逐帧读」。本轮实测：

| 状态 | 数据构造 | 每 update 总时 | 数据占比 |
| --- | ---: | ---: | ---: |
| HEAD（A1/A2 前，batch 2） | 493.81 s 建集 | 2.42–2.63 s（历史 R1） | 计划称 >95% |
| A1 后（batch 2） | 187.66 s | 1.2834 s（workers=0） | — |
| A1+A2+A3 后（batch 4） | 187.66 s | 1.0947 s | **1.2%（0.0137 s/1.12 s）** |

逐段计时（`batch 4`、40 updates、`torch.cuda.synchronize()` 分段）：数据 `0.0137`、
H2D `0.0035`、**fwd+bwd `1.0977`**、优化器 `0.0079`、同步 `0.0`。
⇒ 修完 I/O 之后，**计算重新成为主项（约 97%）**，而不是计划预期的「I/O 占 95%」。
单次 `fwd+bwd` 隔离实测 **1.286 s**（batch 4、K=4、12 步全 BPTT、3,286,037 参数）。
附带实测：`_forward_final` 的两处 `torch.isfinite(...).all()` 不是瓶颈
（裸前向 `0.0475 s` vs 加两次全量 isfinite `0.0471 s`，差值为负，即噪声内）。

**④ 因此本轮的转向依据要改写，而不是删掉。** 转向仍然成立，但理由是
「**同一模型在 ~1 epoch 下被判死的支需要一次算力匹配的重问**」＋「**物理信息这一半是空白**」，
不是「算力富余到可以随便跑几百 epoch」。修完 I/O 后 100 epoch 在 22 年清单上仍需
`128,528 updates × 1.09 s ≈ 39 h/seed`，**仍然贵**，所以 Stage B 的**饱和判定必须真做**，
它决定后面所有 Stage 的成本是否付得起。这一点正是计划 0028 §4 风险 4 与 7 的落地形态。

**⑤ 硬约束不变。** 协议先冻结（R-006）、离线禁网（R-028）、GPU 共驻（R-054）、
`data/raw|interim|processed` 与归档快照只读、不读 2023 test、不改冻结判据。

## Decision

**1. 采用计划 0028 的六 Stage 结构与预算口径**（A 吞吐前置 ~2 GPU-h、B 学习曲线 ~43 GPU-h
硬上限 76 h、C 物理约束 2 轮各 ~64 GPU-h 硬上限 144 h、D 接线+白盒 ~1 GPU-h、E 有界重开
每轮 ~64 GPU-h 上限三轮、F 由用户手选）。**无总 GPU-h 上限**（决策 0030/0038），
`cap`/`remaining` 仅会计；时长按软预算 + 宽松硬上限，超软继续并记 `soft_overrun`。

**2. Stage A 的判据拆成「I/O 侧」与「计算侧」，因为实测证明两者不是同一个量。**
- **A1/A2 的验收是逐位的，且已通过**：`window_sha256` `e8f22c30…`、`usable_windows 32131`、
  `excluded_sample_ids`（11 条，顺序相同）**逐字节不变**；6 个抽样窗口的全部字段
  （张量 sha256、字符串、列表）与 HEAD 代码**零差异**；60 个 batch 的逐 batch sha256
  在 `workers=0` 与 `workers=4` 之间**完全相同**。
- **A 的出口仍然是 batch 4 下 `seconds_per_update < 1.0`，且本轮未达到**：
  实测 **1.0947 s/update**（A1+A2+A3、batch 4），HEAD 同口径见该轮证据页。
  按计划「达不到即停下报告实际倍数，**不改判据**」，本轮**据此报告而不改判据**。
  batch 6/8 的实测见证据页；把 batch 抬到 6+ 属于 Stage F 的成本选项，不属于 A 的出口。
- **A3（同步守卫）与 A4（checkpoint 策略）各需自己的 ADR**，见 0086/0087。

**3. Stage B 的主轴是 updates 而不是 epoch，batch 固定 4。** 理由：R1 已实测 updates 而非
samples 是 skill 的主因；A6 实测 batch 12–14 吞吐饱和（samples/s 1.512）而峰值涨 74%。
在定标期改 batch 会污染「训练量 → skill」这条曲线本身。四个点
0.25/1/4/16 epoch = 2,008/8,033/32,132/128,528 updates，**各自独立跑完、无断点续跑**。

**4. Stage B 的饱和判据冻结为**：`Δ = skill_72h(16 epoch) − skill_72h(4 epoch)`；
`Δ > 0.01` ⇒ 未饱和（最终 run 取 16–64 epoch）；`Δ < 0.005` **且** `skill_72h(16) < skill_72h(4)`
⇒ 饱和（取饱和点）；其余只记录、不外推。**「饱和」是与原始设想相反的结果，必须原样登记。**

**5. Stage E 以 Stage B 的饱和判定为门。** 判定饱和 ⇒ **整段 E 跳过**并把理由写进进度块；
这防止把欠训练误读成方法无效——正是本轮要避免的那个错误。

**6. Stage C 两轮都必须先论证「与已关闭的空间梯度损失不是同一族」。**
那条（`docs/R7_S3_SPATIAL_GRADIENT_LOSS_RESULT.md`）惩罚预测自身梯度、是无目标的平滑先验；
C1 是无目标**约束**（散度/质量一致、比湿非负、露点 ≤ T），C2 是**导数域的目标匹配**
（`|∇·pred − ∇·target|²` 与涡度同款）。论证不成立则**不得开轮**。若 C1 赢，
必须预注册分离束内成分的后续实验，**不得把束当结论**。

**7. Stage F 的配置菜单留给用户手选**，执行者只交付按**实测**吞吐重算的成本表，
不代为选定；batch 只在 F 出现，且必须同时按 updates 折算。

## Consequences

**负面后果（必须如实列出，即本决策的代价）**

1. **A 的出口未达到（1.0947 > 1.0），本轮不改判据。** 这意味着计划 0028 §2 菜单里
   每个数字都要乘上实际倍数（≈1.09 s 实测替换 0.84 s 估计，即约 +30%）。Stage B 的
   43 GPU-h 估计基于 0.84 s/update，按实测 1.0947 s 重算约 **55 GPU-h**；Stage F 菜单里
   「100 epoch / 22 年清单 = 187 h/seed」要改成约 **244 h/seed**。**这些是重算的估计，
   不是实测**，Stage B 跑完后要用真实 s/update 再替换一次。
2. **「95% 时间在 I/O」这一诊断被本轮实测部分否定。** 计划 0028 §0.4 的归因在修完读法后
   不成立（I/O 已降到 1.2%，计算占 97%）。本 ADR 更正它，但**不改写计划 0028 的正文**
   （它是不可变记录）；下游引用该计划时应同时读本 ADR §Context ③。
   这也意味着**大 batch 的收益比计划设想的小**：batch 放大只摊薄固定开销，而固定开销
   已经被 A1/A2 消掉。
3. **逐位相同的验收在 GPU 上不可达，只能在同一线程数下成立。** 实测：同一配置
   `workers=0` 连跑两次，200 个 update 里 **119 个 loss 不同**（首个差异在 update 2、
   差 1 ULP）；`workers=0` vs `workers=4` 差 114 个。单线程（`torch.set_num_threads(1)`）
   下两者**逐位相同**（40/40），CPU 上 `workers=0` 连跑两次也**逐位相同**（60/60）。
   ⇒ 判据必须写成「**固定线程数**下逐位相同」，并把线程数记进 receipt。这是本轮实测
   得到的真实边界，不是放宽判据。
4. **A3 削弱逐样本安全性。** 每步全模型 `isfinite`（155 张量、每 update 一次全设备同步）
   降为每 100 步 + 每 checkpoint，理论上会晚最多 99 步发现 NaN。这是明知交易，
   已写进 0086。
5. **A4 剪 checkpoint 会断审计链**（0068 已有「92 处历史审计引用悬空」先例）。只对新 run
   生效 + 预注册保留清单，见 0087。
6. **Stage B 可能证明「饱和」**，从而否定「几百 epoch」这一原始设想。这是**有效结果**，
   必须如实登记为 negative，不得因不符合预期而改判据或改点。
7. **物理约束可能无效。** legacy 的 `w_wind_div 0.1` 从未在本仓被独立验证；若 C1/C2
   四出口不全真，按预声明永久关闭该支，**不得扫 λ**。
8. **不自动续跑 R4。** 停在 1,440/16,071、无读数，重开是**重跑**约 77 GPU-h，
   属用户决定（训练器 `"no failed-attempt resume is supported"`）。

**正面后果**：数据读取在真实 store 上快 8.9×（每样本 0.5091 → 0.0570 s）、
建集快 2.6×（493.81 → 187.66 s），且 `window_sha256` 与 6 个抽样窗口的全部字段逐位不变——
这是「只改读法、不改语义」的可核查证据。

**否决**：把 A 出口从 1.0 s 放宽到实测值（那是改判据）；把逐位验收降级为
`allclose` 而不记录线程数（掩盖真实边界）；用 batch 8+ 冒充 A 的出口（那是 F 的成本选项）；
按计划 0028 的 0.84 s 估计继续算成本而不重算（会低估 Stage B 约 25%）。
