## §4 选择时必须一并考虑的六条硬约束

这些不是建议，是**已实测的事实**，任何配置都受它们约束：

1. **共驻上限是 batch 10。** batch 12 需 `19,270 + 512 + 6,144 = 25,926 > 24,087 MiB` ⇒
   **必须具名独占授权**。本表里所有 batch ≤ 10 的行都可共驻。
2. **22 年清单上 100 epoch 不可行。** batch 4 时 803,200 updates ⇒ **256.6 GPU-h/seed**、
   三 seed **769.8 GPU-h**（≈ 32 天单卡）。epoch 数必须与清单大小配对。
3. **batch 越大，1 epoch 的 updates 越少**，所以固定 epoch 时**总训练量反而下降**。
   若你要的是「训练量」，应固定 **updates** 而非 epoch，否则跨 batch 不可比。
4. **Stage B 定出的未饱和区间是 16–64 epoch（在 batch 4 上）。** 换成 batch 6/8/10 后
   「16 epoch」不再是同一个训练量（见 §1.4），**不能直接沿用那条规则**。
5. **磁盘**：checkpoint 按决策 0087 稀疏化（每 5,000 步 + 端点）。22 年清单 64 epoch / batch 4 是
   514,112 updates ⇒ 约 103 个 checkpoint × 约 0.055 GiB ≈ **5.7 GiB/臂**；
   三 seed 两臂约 **34 GiB**。当前余 **875 GB**，充足。
6. **三 seed 的双卡墙钟**不是 `3 × 单 seed` 而约为其 **一半**（两卡并行），
   但两臂同跑会乘 **1.09 的争用系数**（§1.2）。本表的 GPU-h 是**计费量**，与墙钟不是一回事。
