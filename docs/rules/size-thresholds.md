## 为什么目标态不做成门禁，而硬上限要做

目标态数字（120 / 100 / 400 / 5 / 8）描述的是**风格偏好**：当前分别有969 / 49 / 64 / 57 / 38处
命中，直接做成门禁会让仓库立刻全红，然后整套规则被忽略。项目刻意使用紧凑的数值代码写法
（例如 `out=Path(output_dir);out.mkdir(...)` 这类一行多语句），以及参数较多但语义清晰的编排函数；
把它们当作违规会迫使作者为过门禁而拆函数，属于规则强加。

硬上限不是风格偏好，而是「这个文件/函数已经需要拆分」的事实判断，取值也在实测分布的尾部之外
（600 行 > p95=580；200 行 > p99=128，只让 5 个入口越线）。因此它落地当天仓库就是绿的，
只约束将来的增长：越线者必须拆成模块，或者——若确有必要——以**决策记录**为代价进入冻结清单。

正确用法：`python tools/check_conventions.py --report` 看目标态趋势；硬上限由默认运行
（也就是 CI 与预提交闸门）执行。
